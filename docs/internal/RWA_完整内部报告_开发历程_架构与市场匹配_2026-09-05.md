## 1. 执行结论

### 1.1 用一句话介绍产品

我们正在建设一套面向机构的 RWA 产品生命周期控制平面：把产品规则、责任机构证据、投资者资格、交易状态、内部账本、外部名册与现金回执组织为可追溯的业务流程，并提供可选的机密凭证证明接入能力。

更适合客户理解的说法是：**让发行人、基金行政、分销商和登记机构，在不把全部敏感数据相互开放的情况下，知道一笔业务由谁批准、依据什么执行、现在卡在哪里、出了差异由谁处理。**

这里的 Network 首先表示机构协作关系，不代表已经拥有一条公链、共识网络或实际接入的机构网络。

### 1.2 现在到底是什么产品

当前最准确的状态是：**具备较完整基金场景、持久化后台、治理与运维组件的本地工程 PoC；已具备较多产品化基础，尚未完成生产安全和外部业务验收。**

它不再只是最初几段密码学模拟代码，也不是一个仅有页面的展示模型。但它仍不能被称为可直接承接真实客户资产的完整生产系统。

### 1.3 核心判断

| 问题 | 本报告结论 |
|---|---|
| 有没有实际工程成果？ | 有：业务、数据、权限、证据、异步、证明接入、运维与测试代码已形成体系。 |
| 自己的内部工作是否全部完成？ | 没有。依赖/系统包风险处置、完整版本证据与独立复核等仍未关闭。 |
| 是不是只能做基金？ | 基础组件可复用，但完整场景以基金为主。其他资产模板不等于其他资产生命周期已完成。 |
| 能否用来演示和谈合作？ | 可以，前提是明确合成数据、模拟外部机构和非生产参数。 |
| 有没有市场匹配？ | 问题方向有外部证据；具体客户愿不愿付费、付多少，尚未证明。 |
| 是否已经胜过主流平台？ | 无法成立。我们有设计侧重点，但缺乏客户、正式审计、长期运行与生态证据。 |
| 最值得先卖什么？ | 机构证据、审批、异常和对账协作模块；不宜先承诺全市场发行、零售入口或流动性。 |
| 马来西亚和阿联酋怎么安排？ | 可作为商业布局目标，但单人阶段宜一个实际交付基地、另一地以伙伴拓展，不急于承担双总部固定成本。 |

### 1.4 现阶段最大的资产与最大的缺口

最大的资产不是“用了 ZK”，而是已经把金融产品运行中容易被忽略的异常处理、状态终局、机构责任和运维边界纳入了设计。

最大的缺口不是再加一个页面，而是三类证据：安全处置完成证据、真实机构集成证据、客户付费与续费证据。现有材料未提供已签客户合同、实际经常性收入、生产机构回执或正式上线批准，本报告不假定它们存在。

## 2. 开发历程：第一步到当前一步

下表依据现存文件与对话重建，表示阶段顺序；没有完整提交历史的阶段不伪造精确开发日期、工时和作者归属。目录名中的 2026-08-19 是项目来源标识，不等于每一项功能的完成日期。

| 5. PostgreSQL 持久化 | 将内存状态改为事务性数据与可恢复状态 | 账本、迁移、审计、幂等、Outbox/Inbox | 数据库提交不代表银行或法定登记完成。 |
| 6. 身份与保密 | 服务端会话、动作授权、CSRF、OIDC/MFA、加密与角色读模型 | 从“切换页面角色”推进到后台身份边界 | OIDC 接口实现不等于真实身份目录已验收；加密不等于零知识。 |

### 2.1 最重要的方向纠偏

最初把“看不见金额”和“能安全经营资产”混在一起；后来明确了两者不同。产品真正需要的是：身份可信、规则可执行、证据有来源、资金与登记有回执、失败可处理、隐私披露可控。密码学是其中一层，不是替代所有机构和业务流程的总开关。

### 2.2 不应重复的历史错误

曾出现“测试通过就说全部完成”“模拟签名也能满足证据门禁”“把 OIDC 模式称为完整生产模式”“把清单或旧测试数字当作当前版本验收”等表述或实现问题。它们的教训是：每一个完成声明必须回答版本、环境、测试对象、验证范围、未覆盖事项五个问题。

## 4. 总体架构

```text
机构操作台 / 投资者界面 / 自动演示向导
                   │
           HTTP API 与服务端会话
                   │
      身份、动作权限、CSRF、租户与产品范围
                   │
  ┌────────────────┼─────────────────┐
  │产品目录与治理   │基金业务工作流    │机密Note工作流
  │机构/证据/审批   │认购/转让/赎回    │输入授权/证明/根确认
  └────────────────┼─────────────────┘
                   │
      PostgreSQL：状态、账本、审计、回执、任务
                   │
       ┌───────────┼─────────────┐
       │Outbox     │机构回调Inbox │隔离Prover任务
       │发布/重试  │验签/顺序/对账 │租约/结果/恢复
       └───────────┼─────────────┘
                   │
   外部机构与基础设施（不同信任域，不是本库事务一部分）
   银行 / 托管 / 登记 / KYC / OIDC / KMS / 根发布与执行系统

横向能力：加密与最小披露、监控、配置检查、迁移、备份、版本证据
```

### 4.1 为什么采用模块化单体加独立 Worker

核心业务共享一个关系数据库，可以用事务维护一致性；耗时证明和外部消息通过独立进程/任务隔离。对单人开发来说，这比过早拆成大量微服务更容易测试和排错。但 Web、Worker、Prover 的资源限制、身份、故障域和扩容仍须分别管理。

这不是去中心化共识架构。数据库、应用管理员、外部事实签发人和参数治理者仍然是信任模型的一部分。

## 5. 把所有角色代入产品

| 角色 | 真实痛点 | 我们的技术作用 | 不能替对方承担的事 |
|---|---|---|---|
| 发行人/管理人 | 产品材料散、审批难追溯、状态不透明 | 规则版本、强制证据、审批与产品控制 | 法律结构、条款真实性、投资管理 |
| 分销/经纪 | 资格反复确认、业务交接易丢字段 | 产品级资格、交易指令、状态跟踪 | 招揽、适当性决定、成交安排 |
| 投资者 | 不知道业务卡在哪里、资料暴露多 | 自己的状态、持有/交易信息和有限披露 | 无条件购买所有资产、收益保证 |
| KYC机构 | 撤销/过期未及时传递 | 签名资格和撤销状态接入 | 身份调查真实性、受益所有人判断 |
| 基金行政/NAV | 多套数字口径、估值时点不一致 | NAV证据、有效期、币种与版本检查 | 估值计算本身及专业责任 |
| 托管机构 | 资产事实与平台账本断开 | 托管证据与回执接口 | 资产保管、抵押/权利真实性 |
| 登记/过户代理 | 内部成交与正式名册不一致 | 名册镜像、顺序回调、差异队列 | 法定持有人认定与最终过户 |
| 银行/现金机构 | 重复请求、资金状态与资产状态错位 | 幂等指令、回执、对账与补偿编排 | 真实资金锁定、支付和资金回滚 |
| 运营经办/复核 | 邮件审批、异常追责困难 | 分离权限、双人控制、不可静默覆盖的记录 | 证明两个账号一定是两个自然人 |
| 审计/监督者 | 证据采集慢、信息过量 | 脱敏证据包、规则/状态/来源链 | 出具专业审计意见或监管批准 |
| 平台技术方 | 接口异构、故障恢复难、责任模糊 | 状态编排、安全实现、测试、运维与交付 | 客户的资产经营、现金、KYC和法律责任 |

平台仍必须对软件质量、权限配置、数据处理、漏洞响应和合同承诺负责。“只做基础设施”不能被理解为软件故障也由合作方负责。

## 6. 数据架构与证据来源

### 6.1 数据不应主要来自抓取公开网页

生产业务需要责任主体提供的数据。公开信息适合市场研究，不足以据此给客户入账、确认投资者资格或激活真实产品。

| 数据 | 权威来源方向 | 接入方式 | 核对重点 |
|---|---|---|---|
| 产品条款 | 发行/管理机构及适当专业方 | 版本化文件摘要与结构化规则 | 生效时间、批准版本、产品范围 |
| 投资者资格 | 分销/KYC机构 | 签名凭证/受控接口 | 主体、产品、期限、撤销、限制 |
| NAV | 基金行政/估值责任方 | 签名证据 | 币种、生效时点、价格范围 |
| 资产和现金 | 托管/银行 | 签名回执或经验证的接口响应 | 引用唯一、金额口径、最终性、撤回语义 |
| 法定登记 | 过户代理/登记机构 | 有顺序的回调、查询与对账 | 谁是真实登记权威、冲正与重放 |
| 根与执行结果 | 指定根发布及执行系统 | 受控确认与可验证引用 | 输入授权绑定、输出根、执行对象 |

### 6.2 是否必须一家一家拿数据

不是先签遍所有机构才能开发。初期选一个设计伙伴、一种资产和一条完整流程，定义最小字段合同；后续优先通过该伙伴已有银行、KYC和登记关系接入。Connector 可减少重复开发，但不能消除商务授权和数据来源认证。

### 6.3 证据必须回答的问题

谁签发、使用哪个密钥版本、针对哪个租户/产品/要求、内容摘要是什么、何时签发和到期、是否撤销、替代了哪个版本、何时验证及由哪个验证器处理。只检查签名字符串长度不构成验签。

代码已引入版本化 canonical payload 与 Ed25519 证据验证；签名密钥管理入口后来又补了登录机构绑定。这些属于实现进展，不构成新的独立审核结论。

### 6.4 数据最小化与跨境

“尽量留在来源机构”是设计原则，不是所有数据完全不流动的证明。签名声明、日志、云运维、备份和 Prover 都可能携带信息。`dataRegion` 字段不能强制网络或云数据驻留；每个部署必须定义实际数据流、存储区域、供应商访问、保留与删除规则。

平台不是可把明文、密钥、个人资料随意送给 AI 的数据池。AI 辅助开发与产品运行数据处理必须分开。

## 7. 业务全流程与双轨结算

### 7.1 产品进入技术可用状态

租户和机构建档 → 机构尽调与双人批准 → 创建草稿产品 → 配齐责任角色 → 提交责任机构证据 → 验证来源、签名和有效期 → 经办发起激活 → 不同身份复核 → 技术 ACTIVE。

ACTIVE 的含义仅是通过系统定义的配置和治理条件，不是政府批准、真实资产担保或可以向所有国家销售。

### 7.2 登记式业务轨 REGISTERED

业务准备 → 产品状态和投资者资格检查 → NAV/币种/额度等核对 → 现金与份额处理编排 → 登记请求/回执 → 内部账本与状态更新 → 审计与对账。

源码 `postgres-store.js` 的主要状态包括：

```text
REQUESTED → POLICY_CHECKED → CASH_RESERVED → REGISTER_PENDING → SETTLED
                       ↘ PROOF_PENDING → ROOT_PENDING → SETTLED

异常分支：REQUIRES_REVIEW → PENDING_APPROVAL → REPLACED / CANCELLED
允许的拒绝分支：REJECTED
```

这是对源码状态名的摘要，不是早期 PRD 中 CREATED/ASSET_LOCKED 等概念图的逐字复制。实际状态转换由代码和数据库约束决定。

### 7.3 机密 Note 轨 CONFIDENTIAL_NOTE

1. 经纪提交业务指令，包含产品、接收对象、费用、有效期和幂等键。
2. 服务端从会话、产品及固定上下文取得租户、资产类型和 contextId，不让请求任意覆盖。
3. 提供并冻结13项公开输入，对业务字段重新比较。
4. Prover任务生成证明；业务服务不应把 witness 当作普通日志或公开请求字段。
5. 固定验证器校验证明与公开输入；数据库原子记录证明接受、nullifier和输出承诺。
6. 此时状态为 ROOT_PENDING，不是银行/法定登记终局。
7. 根发布和执行效果经受权流程确认，两个不同 principal 完成经办/复核，进入机密账本 SETTLED。
8. 法定登记是否完成另行记录；不能把 `settlementApplied:true` 解释成现实世界所有账本都已更新。

### 7.4 认购与赎回必须区分两条轨道

基金演示/登记式工作流有认购和赎回，不等于已经实现了机密 Note 的完整存入铸造、首次 Note 自举、提现销毁、现金发放和法定名册桥接。固定 2-in/2-out 转让候选本身没有解决全部入口出口问题。后续产品合同必须明确客户要的是登记轨、机密转让轨，还是两者间的完整桥接；不能把它们打包成已交付事实。

### 7.5 异常如何处理

资格撤销、余额不足、价格越界等尽量在产生外部效果前拒绝；登记失败、超时或对账差异进入异常队列。重试要重新验证现时条件，不得自动沿用已经过期的资格。已经发生不可逆外部效果时，依赖查询、补偿和人工控制，不能简单删掉本地记录假装没有交易。

## 8. 密码学与隐私：哪些是真实能力

### 8.1 三种机制不能混称

| 机制 | 当前用途 | 不提供什么 |
|---|---|---|
| AES-GCM/KMS信封 | 加密敏感载荷、数据密钥封装和轮换接口 | 不证明业务金额守恒；授权解密方仍能看到数据 |
| HMAC-SHA256经济字段记录 | 将字段与租户/交易/产品等上下文绑定 | 不是公众可验证的Pedersen承诺，也不是ZK证明 |
| Groth16及候选电路 | 在指定约束下验证机密Note转让关系 | 不证明银行资金、底层资产真实或法定权益有效 |

### 8.2 当前候选电路的形状

固定两个真实输入 Note、两个输出 Note，没有可选占位输入。金额64位，资产类型32位，nonce128位，blinding248位；ownerPubKey通过严格域元素分解和填充进入99字节的承诺消息。链下 Pedersen 输出是压缩点，必须按约定解包坐标。

输入所有权通过由秘密推导的 ownerPubKey 关系表达；输出可以只绑定收款方公钥，不应要求发送方获取收款方秘密。金额约束为 `input0 + input1 = output0 + output1 + fee`。

这里使用 circomlib 对消息位串的 Pedersen 构造，不能据此对外承诺“任意业务金额承诺可直接相加完成会计清算”。业务守恒仍由电路和账本逻辑分别保证。

### 8.3 固定13项公开输入

顺序为：merkleRoot、contextId、assetType、fee、recipient、relayer、transactionHash、两个输入nullifier、两个输出X坐标、两个输出Y坐标。坐标序列是 X0、X1、Y0、Y1，不能擅自换成 X0、Y0、X1、Y1。

资产类型、费用和执行对象等公开字段不被ZK自动隐藏。公开输入也可能提供关联线索，所以不能宣传“完全匿名、无法追踪”。

### 8.4 transactionHash 与上下文

应用将全部13项公开输入与已授权版本逐项比较，再交真实验证器。防止业务字段被替换，依赖的不是一个名叫 transactionHash 的字段，而是电路/验证产物、公开输入和应用授权的一致绑定。上下文改变后旧 Note/证明如何迁移，需要升级治理；不能随意更换域标签或版本参数。

### 8.5 已验证与未验证

本地存在真 Groth16 正反测试、短生命周期验证子进程及数据库接受测试。macOS与同机Linux VM构建得到相同 R1CS/SYM/WASM 哈希，是跨OS复现，不是独立物理主机复现。

新单机测试来源链经历失败后通过了R1CS/PTAU/zkey关系检查与新证明验证；测试参数公开且不可信，严禁生产。历史fixture缺少对应proving key的来源证据，未因新测试链成功而自动补齐。正式参数、产物批准、证明服务以及终局桥接还不能认定完成。

## 9. 数据库、异步与恢复

金融状态使用 Serializable 事务与有限重试，账本按资产代码分别平衡，金额以整数处理。对同一个client的查询近期改成逐条await，保持事务隔离语义。迁移数量当前到021，迁移哈希与审批顺序用于避免数据库状态漂移。

Outbox在业务事务中保存待发送事件；Inbox对接收事件去重。外部发送成功后、本地确认前仍可能崩溃，所以语义是 at-least-once，不是全链路 exactly-once。对端必须基于稳定事件ID幂等，并提供状态查询或回执。

队列抢占采用 Read Committed 配合行锁，与金融事务的 Serializable 分开。历史压力测试发现并修正了并发下40001重试耗尽，不能因为“隔离级别越高越好”而所有查询一律Serializable。

审计哈希链用于发现记录变更，但不能自动抵抗拥有数据库及日志全权的管理员重写整条链。若客户需要独立防篡改证明，应定义外部锚定、受控审计存储和管理员职责分离；本报告不认定这些已经生产验收。

备份脚本存在不等于灾备能力已经认证。生产必须实测能恢复哪些数据库、密钥版本、证据文件与任务状态，并度量实际恢复时间和丢失窗口。

## 10. 部署与监控

当前有本地PoC容器和生产示例配置。生产示例要求明确profile、持久化数据库、OIDC、KMS/provider、产物固定和非演示租户，先配置检查、产物检查、迁移，再启动各服务。示例不是可不填任何外部配置的一键生产产品。

本地验收容器为非root、只读运行文件系统、回环端口；运行层排除开发依赖与npm CLI。数据库卷和开发密钥卷保留。生产外部provider应经评审并受控挂载，不能由用户提交任意代码路径。

监控涵盖Web、数据库、主机、Outbox和Prover。历史原生记录包括34条规则、40个场景fixture和26个Grafana面板；代表性浏览器视觉检查完成。本地告警触发/恢复到合成接收器，不等于生产电话、邮件或值班轮班已就绪。无样本的p95空图不能读作0延迟。

暂无可支持“多少并发客户”“每秒多少真实ZK转账”“99.99% SLA”的充分生产证据。合成事件压力测试不能直接换算为商业容量。

## 12. 真正解决什么，不能解决什么

### 12.1 高匹配的问题

- 机构之间互相等待，却不知道缺哪份证据：强制清单、责任人和状态能降低沟通歧义。
- 产品条款调整后操作仍沿用旧规则：版本化和执行时校验有直接作用。
- 重复请求、超时回调、登记与平台不一致：幂等、顺序、异常和对账可降低重复处理。
- 审计时临时拼邮件与截图：结构化证据包可减少整理工作。
- 不同机构不愿共享全部敏感字段：角色披露与加密可减少不必要暴露；ZK在真正需要时补充。

以上是“技术机制能对应痛点”的判断。减少多少工时和差错，必须在客户基线下测量。

### 12.2 无法靠这套软件单独解决

资产无人购买、基金业绩差、交易流动性不足、发行人违约、真实数据虚假、机构拒绝接口、某市场不允许某类销售、银行不支持最终性语义、客户采购不愿承担单人供应商风险。这些不是再加一个电路就能消失的问题。

### 12.3 对“让普通人进入RWA”的回答

可以通过机构的投资者入口改善体验，但资格、最低认购、赎回安排和销售范围仍由产品与适用规则决定。本产品更适合先提高机构后台效率，再由合格分销方服务终端客户；暂不把自己改成面向所有人的零售资产超市。

| Tokeny | 发行、管理、转移证券；API、白标平台、ERC-3643许可型代币 | 直接重叠于生命周期与身份规则，也可作为链上发行组件 | 不能因我们有ZK候选就宣称安全/产品成熟度超过它。 |
| Libeara | 机构基金和债务工具代币化、发行分销与治理 | 与基金基础设施定位重叠 | 不知道其内部所有实现，不能断言它没有隐私或异常能力。 |
| Marketnode | Gateway代币化资产、Fundnode基金网络、Smartflow工作流 | 后台协作和数据工作流的直接竞争/潜在合作对象 | 不能说运营控制和对账没人做；其网络关系也是壁垒。 |
| 客户原有系统＋人工 | 现有登记、估值、邮件审批、表格 | 实际最常见替代方案 | 即使技术落后，切换风险低也可能让客户继续使用。 |

上述能力依据厂商公开说明，不等于本报告进行了竞品安全审计或验证全部宣传。[Tokeny产品文档](https://docs.tokeny.com/docs/solutions-overview-1)；[Libeara方案](https://libeara.com/solutions/)；[Marketnode产品主页](https://www.marketnode.com/)

### 14.2 我们可能形成的差异化

1. 对技术终局、现金和法定登记严格分层，减少错误的“已经完成”状态。
2. 把证据有效期、来源、密钥、机构责任和产品激活串成一个操作流程。
3. 专注小范围机构协作，允许客户保留现有发行和登记系统，而非要求全面更换。
4. 用可演示的失败恢复和交接证据降低客户试用成本。
5. 在真实保密需求存在时接入机密Note，不强迫所有业务都使用ZK。

这些是可验证的产品主张，不是已形成护城河。竞争对手可能拥有同类机制；护城河要由实际连接器、客户嵌入深度、运行历史和交付方法积累。

### 14.3 “哪个架构更先进”的正确拆法

按密码学表达能力、业务覆盖、互操作、隐私边界、可恢复性、供应链治理、部署成本和客户网络分别比较。我们在某些设计取舍上清晰，不代表其他维度领先。开源密码学库本身不是专有壁垒；正式审计和生产运行经验也不能由代码复杂度替代。

## 15. 商业机会与产品组合

### 15.1 建议最先交付的窄产品

**产品证据与异常协作工作台**：服务一个基金管理/行政链条，提供产品配置、证据到期提醒、审批、交易状态、回执对账和审计导出。优先附着在客户现有系统旁，不先替换核心名册和银行系统。

当前生产示例强制完整Groth16/provider条件；如果要单独销售非ZK证据工作台，需要设计和验收一个明确的模块化交付配置，不能简单关闭现有校验后称为新产品。这是后续可选工程，不是当前已完成能力。

### 15.2 三层产品包装建议

| 层 | 客户购买什么 | 当前基础 | 新承诺前的条件 |
|---|---|---|---|
| A 证据与治理 | 机构、规则、审批、证据包 | 较充分 | 最小部署配置、客户字段、安全收尾 |
| B 生命周期协作 | 认购/转让/赎回、对账、外部连接器 | 基金合成流程与SDK | 实际接口与最终性合同 |
| C 机密转让 | 可选ZK验证和Note流程 | 本地候选验证链 | 正式产物、Prover、根/执行与入口出口方案 |

模块A最容易解释价值，模块C技术门槛高但销售阻力和交付责任也高。不要用C的愿景掩盖A是否有人愿意付钱。

### 15.3 值得客户访谈验证的机会

- 证据过期和机构授权变更如何影响在途交易；
- 多机构系统不同步时，能否输出一个共同认可的异常交接包；
- 产品规则升级前后哪些交易沿用哪一版，如何解释；
- 既有代币化平台之外的独立对账和证据出口；
- 后续Sukuk流程中的责任证据、分配和事件治理。

这些是本产品可探索的细分方向，不能声称“别人没有发现”。特别是Sukuk涉及专业结构与分配规则，目录里出现名称并不等于具备专业处理能力。

## 16. 定价、成本与盈利模型

本节为内部试算，不是市场报价或收入预测；金额以美元记账便于跨市场比较，不包含汇率假设。需要访谈和正式成本询价替换。

### 16.1 收费结构建议

采用“付费PoC/接入费＋年度平台订阅＋明确范围的支持服务”，特殊连接器单独报价。按租户、产品数、事件量和服务等级划界。没有真实业务与法律核对前，不把交易额分成或资产管理费作为默认商业模式。

探索报价可设计为：有限PoC总价3,000–10,000；初始集成5,000–20,000；年度订阅12,000–36,000。仅为询价测试区间，未证明客户愿意支付，也不保证覆盖高要求银行交付成本。

### 16.2 自下而上的市场空间

不要用全球RWA资产价值乘费率估计我们的市场。更合理的模型：可接触的机构数量 × 有明确痛点且有预算的比例 × 成交率 × 年合同金额。

例如一个纯假设的销售漏斗：联系30家 → 10家有效访谈 → 3家付费PoC → 1家年约。它是资源规划情景，不是预测概率。对单人团队，一家可续费客户比四国都建立公司更有验证价值。

### 16.3 年度情景

| 情景（假设） | 年约客户 | 每客户年费 | 经常性收入 | 解释 |
|---|---:|---:|---:|---|
| 验证期 | 1 | 12,000 | 12,000 | 有付费信号，不足以证明可持续经营 |
| 小规模 | 3 | 24,000 | 72,000 | 若交付范围严格，可支持精简经营的可能性 |
| 扩展期 | 8 | 36,000 | 288,000 | 需要支持、交付和销售容量，不能仍按单人零成本算 |

一次性集成收入不计入ARR，订阅收入也不等于利润。利润还要扣部署、支持、审计摊销、销售、工具、保险/专业服务和税费。

### 16.4 盈亏平衡示例

假设年费24,000、每客户直接服务成本6,000，则每客户贡献18,000。若年固定现金成本36,000，约2家覆盖该现金口径；若另外计入创始人劳动成本36,000，则需约4家。以上没有计入突发整改和税费，不能当作融资预测。

### 16.5 谁承担什么成本

我们承担开发工具、软件维护、技术安全、合同内支持、连接器开发和自身交付费用。合作机构承担自己的发行管理、KYC调查、托管、银行、登记和其自身专业人员，但接口联调工时及云服务由合同约定。客户私有部署也不会把我们的技术支持成本降成零。

### 16.6 AI能减少什么

可加速样板代码、测试准备、文档和需求归纳。不能把正式验收、机构事实确认、密钥控制、值班责任和客户关系全部替代。本项目已经发生过AI互查后仍遗漏问题，预算中必须保留验证成本。AI订阅费不是产品开发的全部成本。

## 17. 单人团队如何落地

优先顺序应是：一个付费问题 → 一个伙伴 → 一个可交付模块 → 一套重复交付方法。不要同时运营零售平台、四国营销、全部资产类别和全天候托管式服务。

建议创始人主抓产品/客户，AI辅助受控实现和资料，按里程碑购买独立审查与必要专业服务。不承诺无人值班的24/7高等级SLA；对关键生产故障必须有备用联系人、维护窗口和客户处置权限。

马来西亚与阿联酋双市场计划可以保留，但注册、办公、签证、税务和当地服务采购都应以正式资格及现金流为依据，本报告不为这些费用作未经核实的价格承诺。

## 18. 客户认可：不是看完演示就算成功

### 18.1 访谈必须问的八个问题

1. 最近一次跨机构业务失败是什么，处理用了多久？
2. 哪个岗位重复录入或等待回执最多？
3. 数据谁有权提供，谁能签接口合同？
4. 哪套系统是法定名册权威，哪个时间点不可逆？
5. 每月异常量和人工工时是多少？
6. 哪些字段绝对不能离开现有环境？
7. 谁批准预算，是否允许小额付费试点？
8. 什么结果会让其续费，什么情况必须停止？

### 18.2 付费PoC建议验收指标

在客户同意的数据范围内，比较当前流程与新流程的证据准备耗时、异常发现时间、人工重复录入次数、在途交易可见性和资料完整率。设定目标前先测基线，不先承诺“节省80%”。

明确验收数据、样本量、失败场景、参与机构、责任人、交付物、付款节点和退出导出。客户必须能拿走自己的数据，不能用数据锁定代替产品价值。

### 18.3 向客户证明可信度的材料

可复现演示、真实版本清单、接口合同、权限矩阵、已知限制、恢复演练结果、支持边界、第三方组件清单、变更记录和待关闭事项。不能用AI生成的“审计通过”字样替代独立报告。

| 门槛 | 内部可完成的工作 | 需要共同或独立完成的工作 | 判定标准 |

目前不宜再承诺精确“几天全部结束”。内部维护可估工时，独立渠道、上游补丁和机构联调是另外的日历时间。进度以完成门槛计，而不是累计运行测试次数。

## 20. 融资与扶持申请叙事

适合的叙事：我们为受监管机构提供可部署的软件控制层，已具备基金场景工程PoC、机构证据和异常协作、保密数据处理及可选证明适配；下一步验证真实机构交付和可重复收入。

不适合的叙事：全球RWA底层已全部完成、能绕过中介和资格要求、已有银行级安全背书、跨四国完全合规、完全自动化不需要人。

融资材料应突出问题案例、买方角色、PoC合同、单客户交付成本、现有工程证据、遗留风险与资金用途。政策材料应说明拟落地的实际研发、商业化、本地供应链与岗位，而不是承诺尚未发生的税收和客户。

## 22. 创始人常见问题的统一口径

**架构完成了吗？** 主要工程体系已形成；内部安全收尾和生产验收未完成。

**有竞争力吗？** 有形成细分优势的基础；没有证据证明已胜过成熟平台或已有PMF。

**是不是只差外部？** 不是。风险处置、版本化验收和产品边界仍有内部任务。

**能不能申请支持或融资？** 可以准备并如实描述阶段；获得支持与否不能由代码数量判断。

**会不会全部白做？** 现有工程可作为模块化基础；但如果没有客户验证，继续增加功能不一定增加商业价值。

**数据怎么办？** 从一个伙伴的最小真实授权数据契约开始，合成数据用于开发；不先汇集所有机构数据库。

**谁负责合规人员？** 客户承担自身受监管业务职责；我们仍负责软件和自身经营的责任，具体合同和法律意见确认。

**什么时候算成功？** 第一阶段是一个客户付费验证且愿意继续使用；下一阶段是第二个客户能低成本复用，而非每家重写。

## 最终内部结论

这套工程已经从不可靠的密码学模拟，发展为围绕基金机构协作的模块化控制平面。它有真实的代码与本地验证成果，也有必须继续完成的内部工程和独立验收。

商业上，最合理的路线不是声称建立一个覆盖所有RWA的全能平台，而是先把产品证据、审批、异常和对账做成客户愿意付费的模块，再按需求扩展生命周期与机密转让。

**保留技术长期方向，缩小第一单交付范围；以证据证明安全边界，以付费验证市场，而不是用功能数量证明成功。**
