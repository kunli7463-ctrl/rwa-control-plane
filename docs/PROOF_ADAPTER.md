# Proof Adapter security boundary

The local material found under `~/Downloads/zk_audit_cloud` is a V2 fixed 2-in/2-out JoinSplit audit candidate, not a V3 production artifact. Its own documentation says it is not production ready, and the inspected directory does not contain an approved proving key, verification key manifest or deployment ceremony record. The control plane therefore does not copy that circuit into production or claim that ZK is enabled.

`Groth16JoinSplitProofAdapter` defines the application verification boundary. At startup it pins:

- protocol and curve;
- circuit identifier and semantic version;
- the exact 13-item public-signal order;
- the approved verification-key SHA-256 hash;
- a concrete verifier implementation.

The 13 signals do not all have the same owner. Before proof acceptance, the server reads `contextId` and `assetType` from the product's immutable active ZK context, and `fee`, `recipient` and `relayer` from an append-only execution instruction bound to the transaction request hash. The prover supplies the recognized Merkle root, circuit-derived `transactionHash`, two nullifiers and four output coordinates. The gate freezes the combined 13-item package, then compares every verified public signal with that frozen package. At final acceptance it locks and rechecks the transaction state, execution instruction and still-active product context, so a proof generated before context retirement fails closed.

The application deliberately does not implement a second Poseidon `transactionHash` function with different dependencies. In the real circuit that hash is constrained over the five server-owned fields plus the prover-state fields; pinning every public signal and using the real verifier closes that binding.

The regression suite now includes a real local-only Groth16 vector generated from the candidate circuit with Circom 2.1.6, `circomlib@2.0.5` and `snarkjs@0.7.6`. It verifies a valid proof, rejects a consistently relabelled public input, rejects a modified proof coordinate, and crosses the PostgreSQL authorization/acceptance gate. The vector's single-machine ceremony is deliberately untrusted and is marked `DO_NOT_DEPLOY`; it proves runtime interoperability, not production ceremony safety or circuit approval.

`SandboxNoProofAdapter` always returns `verified: false` and `productionAcceptable: false`. It exists only so the UI can accurately demonstrate workflows without pretending that a proof was checked.

The application records verified proof acceptance in the `CONFIDENTIAL_PROOF_REGISTRY` domain and moves the transaction to `ROOT_PENDING` in one PostgreSQL transaction. A separately authorized finalization call must attest authoritative root publication and the proof-bound execution effects before the transaction reaches `CONFIDENTIAL_NOTE_LEDGER / SETTLED`. Production still requires a separately approved circuit package, reproducible build, phase-2 ceremony or explicitly governed universal setup, independent audit, production verification key, prover service, artifact registry, root publisher/effects adapter, and an institution-approved bridge to the legal register. Until those exist, production must fail closed instead of falling back to the sandbox adapter.

The runtime loader expects a bundle containing `manifest.json` and its referenced verification-key JSON. The manifest schema is `rwa.groth16-artifact.v1` and contains exactly `schema`, `protocol`, `curve`, `circuitId`, `circuitVersion`, `publicSignalOrder`, and `verificationKey { path, sha256 }`. The deployment configuration pins the raw manifest file through `ZK_ARTIFACT_MANIFEST_SHA256`; the manifest pins the raw verification-key file. Bundle paths are confined, manifest/vkey/proof sizes are bounded, and proof shape is validated before cryptographic work. `npm run zk:verify-artifacts` performs the read-only startup check. No proving key or trusted-setup material is generated by the control plane.

`snarkjs@0.7.6` does not terminate the BN254 worker pool created by its public `groth16.verify` API. Calling it directly in a long-lived Web process leaks worker lifetime. Production verification therefore runs the official API in a short-lived child process with a 15-second timeout, bounded input/output, and fail-closed crash handling. The child exits after one result, while the Web process never loads proof-controlled data into an unbounded worker pool.

The lockfile overrides `snarkjs`'s compatible CLI-only dependency to `bfj@7.0.2`, avoiding the vulnerable `bfj@7.1.0 → jsonpath → underscore` chain. `npm audit --omit=dev` reports zero production vulnerabilities. Development-only `circomlibjs` dependencies still produce audit findings and must never be shipped in the runtime image.
